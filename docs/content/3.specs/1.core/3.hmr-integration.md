# Task 1.3: HMR-Integration fuer JSON-Inhalte

**Epic:** 1 — Core Framework & Nuxt Module Logic
**Status:** Spezifikation
**Abhaengigkeiten:** Task 1.1 (Module-Hooks), Task 1.2 (Storage Bridge)

---

## 1. Ziel

Hot Module Replacement (HMR) fuer JSON-Content-Dateien im `content/`-Verzeichnis. Wenn eine JSON-Datei geaendert wird (durch den Editor ODER externe Tools wie VS Code), soll die laufende Nuxt-Dev-Instanz:
- Die Aenderung erkennen
- Den betroffenen Content neu laden (ohne Full-Page-Reload)
- Die Vue-Komponenten mit den neuen Daten aktualisieren
- Den Editor-State synchronisieren

## 2. Problemstellung

Nuxt 3 hat eingebautes HMR fuer Vue-Komponenten, TypeScript/JavaScript, CSS/SCSS und Nuxt Content Module. **Nicht abgedeckt** sind beliebige JSON-Dateien ausserhalb von `node_modules` und `public/`.

## 3. Technisches Design

### 3.1 Architektur-Uebersicht

```
content/pages/about.json  (Datei aendert sich)
        |
        v
  [Chokidar / Bun Watcher]
        |
        v
  [Nuxt Hook: builder:watch]
        |
        |-- Datei-Typ erkennen (page / site / navigation)
        |-- Betroffenen Slug extrahieren
        +-- WebSocket-Event an Client senden
              |
              v
        [Client: HMR Handler]
              |
              |-- Content ueber API neu fetchen
              |-- Reactive State aktualisieren
              +-- Vue re-rendert betroffene Komponenten
```

### 3.2 Server-Side: File Watcher Integration

#### `builder:watch` Hook

```typescript
if (nuxt.options.dev) {
  const contentDir = resolver.resolve(nuxt.options.rootDir, options.contentDir)
  nuxt.options.watch.push(contentDir)

  nuxt.hook('builder:watch', async (event, relativePath) => {
    if (!relativePath.startsWith(options.contentDir)) return
    if (!relativePath.endsWith('.json')) return

    const contentType = resolveContentType(relativePath, options.contentDir)
    if (!contentType) return

    nuxt.callHook('openpress:content-change', {
      event,
      path: relativePath,
      contentType,
      timestamp: Date.now()
    })
  })
}
```

#### Content-Type Resolution

```typescript
type ContentType =
  | { type: 'page'; slug: string }
  | { type: 'site' }
  | { type: 'navigation' }

function resolveContentType(relativePath: string, contentDir: string): ContentType | null {
  const normalized = relativePath.replace(contentDir + '/', '').replace(/\\/g, '/')

  if (normalized.startsWith('pages/') && normalized.endsWith('.json')) {
    const slug = normalized.replace('pages/', '').replace('.json', '')
    return { type: 'page', slug }
  }
  if (normalized === 'site.json') return { type: 'site' }
  if (normalized === 'navigation.json') return { type: 'navigation' }
  return null
}
```

### 3.3 Client-Side: HMR Event Handler

```typescript
// runtime/plugins/openpress-hmr.client.ts (Dev-Only)
export default defineNuxtPlugin(() => {
  if (!import.meta.hot) return

  import.meta.hot.on('openpress:content-change', (payload) => {
    handleContentChange(payload)
  })
})
```

### 3.4 Reactive State Invalidation

```typescript
export function useContentRefresh() {
  async function refreshPage(slug: string, event: string) {
    if (event === 'unlink') {
      await navigateTo('/_edit')
      return
    }
    await refreshNuxtData(`openpress-page-${slug}`)
  }

  async function refreshSiteConfig() {
    await refreshNuxtData('openpress-site')
  }

  async function refreshNavigation() {
    await refreshNuxtData('openpress-navigation')
  }

  return { refreshPage, refreshSiteConfig, refreshNavigation }
}
```

## 4. Szenarien

### Editor speichert Page

1. User klickt "Speichern"
2. Client: PUT `/api/_openpress/pages/about`
3. Server: `writePage()` schreibt `about.json`
4. File-Watcher erkennt Aenderung
5. WebSocket-Event an Client
6. Client: `refreshNuxtData` -> Vue re-rendert

### Externe Bearbeitung (VS Code)

1. Developer aendert `about.json` in VS Code
2. File-Watcher erkennt Aenderung
3. WebSocket-Event an Client
4. Browser zeigt aktualisierten Content (kein Reload noetig)

### Neue Page erstellt

1. File-Watcher: 'add' Event
2. Client: Page-Liste invalidieren
3. Editor-Sidebar zeigt neue Seite

### Page geloescht

1. File-Watcher: 'unlink' Event
2. Client navigiert zum Dashboard
3. Page-Liste wird invalidiert

## 5. Edge Cases

### Rapid File Changes (Debouncing)

100ms Debounce — schnell genug fuer fluessiges Feedback, vermeidet aber Ueberlastung bei Batch-Operations.

### Ungueltige JSON-Dateien

Der Client behaelt die letzten gueltigen Daten. Sobald die Datei wieder valide ist, wird der naechste Watch-Event den Refresh erneut triggern.

### Dev-Only Scoping

Alle HMR-Komponenten sind ausschliesslich im Development-Modus aktiv. In Production kommuniziert der Editor ueber die REST-API.

## 6. Testplan

| Test | Beschreibung |
|------|-------------|
| `resolveContentType` | Korrekte Zuordnung von Pfaden zu Content-Types |
| Slug-Extraktion | `pages/about.json` -> `about` |
| Ignorierte Pfade | Nicht-JSON-Dateien werden ignoriert |
| Page-Aenderung | JSON-Datei aendern -> Client erhaelt Update |
| Neue Datei | Page-JSON erstellen -> erscheint in der Liste |
| Datei loeschen | Page-JSON loeschen -> Editor navigiert weg |
| Ungueltige JSON | Kein Crash, letzte Daten bleiben |

## 7. Akzeptanzkriterien

- JSON-Aenderungen in `content/` werden im Dev-Modus erkannt
- Page-Aenderungen aktualisieren die Vorschau ohne Full-Page-Reload
- Site-Config-Aenderungen werden sofort reflektiert
- Navigation-Aenderungen aktualisieren das Menue live
- Neue Pages erscheinen automatisch in der Editor-Sidebar
- Geloeschte Pages loesen Navigation zum Dashboard aus
- Ungueltige JSON-Dateien verursachen keinen Crash
- HMR-Code ist nicht im Production-Build enthalten
