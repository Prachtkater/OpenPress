# Task 2.3: Tailwind-Klassen-Mapping System (Nuxt UI Style)

**EPIC:** 2 — UI Engine & Component Bridge (Op-System)
**Paket:** `@openpress/ui`
**Pfad:** `packages/ui/src/runtime/theme/`
**Abhaengigkeiten:** Task 2.1 (OpProvider), Task 2.2 (OpSection/OpSlot)

---

## 1. Zielsetzung

Ein Theme-System nach dem Vorbild von Nuxt UI, das Tailwind-Klassen ueber eine strukturierte API an Op-Komponenten verteilt. Themes definieren Klassen-Mappings fuer Slots und Variants — Komponenten konsumieren sie via Composable. Overrides sind auf drei Ebenen moeglich: Theme-Default -> `app.config.ts` -> `ui` Prop.

**Kernprinzip:** Striktes Feature/Theme Separation. Op-Komponenten enthalten **null** Tailwind-Klassen. Alle visuellen Klassen kommen aus dem Theme-Layer.

## 2. Konzept-Uebersicht

### Nuxt UI als Vorbild

Nuxt UI definiert pro Komponente ein Theme-Objekt mit Slots, Variants und Compound Variants. OpenPress uebernimmt dieses Pattern 1:1 fuer die Op-Komponentenhierarchie.

### OpenPress Adaption

```typescript
export default {
  slots: {
    root: '',
    inner: '',
  },
  variants: {
    type: {
      hero: {
        root: 'relative overflow-hidden',
        inner: 'mx-auto max-w-7xl px-6 py-24 lg:px-8',
      },
      features: {
        root: 'bg-gray-50 dark:bg-gray-900',
        inner: 'mx-auto max-w-7xl px-6 py-16 lg:px-8',
      },
    },
  },
  defaultVariants: {},
}
```

## 4. Klassen-Resolution Engine

### Merge-Reihenfolge (Prioritaet aufsteigend)

```
1. Theme-Default (slots)           <-- Basis-Klassen aus dem Theme
2. Theme-Variants                  <-- Klassen basierend auf aktiven Variants
3. Theme-CompoundVariants          <-- Klassen wenn mehrere Variants matchen
4. app.config.ts Overrides         <-- Globale User-Overrides
5. ui Prop                         <-- Instanz-spezifische Overrides
```

**Tailwind Merge:** Auf jeder Stufe werden Klassen mit `tailwind-merge` zusammengefuehrt, sodass spaetere Werte konfligierende fruehere ueberschreiben.

### `resolveComponentClasses()`

```typescript
export function resolveComponentClasses(
  theme: OpComponentTheme,
  activeVariants: Record<string, string>,
  configOverrides?: Partial<Record<string, string>>,
  uiOverrides?: Partial<Record<string, string>>,
): ResolvedClasses {
  const slotNames = Object.keys(theme.slots)
  const result: ResolvedClasses = {}

  for (const slot of slotNames) {
    const layers: string[] = []

    // Layer 1: Base Slot Klassen
    if (theme.slots[slot]) layers.push(theme.slots[slot])

    // Layer 2: Variant Klassen
    if (theme.variants) {
      const merged = { ...theme.defaultVariants, ...activeVariants }
      for (const [variantName, variantValue] of Object.entries(merged)) {
        const variantClasses = theme.variants[variantName]?.[variantValue]?.[slot]
        if (variantClasses) layers.push(variantClasses)
      }
    }

    // Layer 3: Compound Variants
    // Layer 4: app.config.ts Overrides
    // Layer 5: ui Prop Overrides

    result[slot] = twMerge(...layers)
  }

  return result
}
```

## 5. Composable: `useOpThemeClasses()`

```typescript
export function useOpThemeClasses(
  component: 'section' | 'slot' | 'provider',
  variant?: string,
  uiOverrides?: Partial<Record<string, string>>,
): ResolvedClasses
```

Gibt reaktive, computed Klassen zurueck.

## 7. Tailwind Merge

Ohne tailwind-merge:
```
Theme:  "px-6 py-24"
Config: "px-8"
Result: "px-6 py-24 px-8"   <-- KONFLIKT
```

Mit tailwind-merge:
```
Theme:  "px-6 py-24"
Config: "px-8"
Result: "py-24 px-8"        <-- KORREKT
```

## 8. End-to-End Beispiel

### Theme-Autor definiert Klassen:

```typescript
export const section = {
  slots: { root: 'relative', inner: 'mx-auto max-w-7xl' },
  variants: { type: { hero: { root: 'min-h-[60vh]', inner: 'px-6 py-24' } } },
}
```

### User ueberschreibt global:

```typescript
export default defineAppConfig({
  op: { section: { inner: 'max-w-6xl' } },
})
```

### Komponente ueberschreibt lokal:

```vue
<OpSection :section="section" :ui="{ root: 'bg-black' }" />
```

### Resultierende Klassen fuer `root` (Section type="hero"):

```
Theme base:    "relative"
+ Variant:     "min-h-[60vh]"
+ ui Prop:     "bg-black"
= twMerge:     "relative min-h-[60vh] bg-black"
```

### Resultierende Klassen fuer `inner`:

```
Theme base:    "mx-auto max-w-7xl"
+ Variant:     "px-6 py-24"
+ Config:      "max-w-6xl"
= twMerge:     "mx-auto max-w-6xl px-6 py-24"
```

## 9. Dark Mode

OpenPress verwendet **keine eigene** Dark-Mode-Logik. Das System baut auf Tailwinds `dark:` Variante auf. Der Dark-Mode-Toggle ist Sache der Host-Applikation.

## 10. Testplan

| Test | Beschreibung |
|------|-------------|
| Base Slots | Nur Basis-Klassen ohne Variants |
| Single Variant | `type: 'hero'` -> korrekte Klassen |
| Default Variants | `defaultVariants` werden angewendet |
| Variant Override | Aktive Variants ueberschreiben Defaults |
| Compound Variants | Mehrere Conditions -> Match |
| Config Override | app.config.ts Werte ueberschreiben Theme |
| UI Prop Override | `ui` Prop ueberschreibt alles |
| Tailwind Merge | Konfligierende Klassen werden korrekt gemerged |
| Empty Theme | Fehlende Theme-Definition -> leere Klassen |
| Block Theme | Block-spezifische Klassen werden aufgeloest |
| useOpThemeClasses | Composable gibt reaktive Klassen zurueck |

## 11. Akzeptanzkriterien

- `OpComponentTheme` Type mit slots, variants, compoundVariants, defaultVariants
- `resolveComponentClasses()` merged 5 Layers korrekt
- `tailwind-merge` Integration fuer konfliktfreies Merging
- `useOpThemeClasses()` Composable mit reaktivem Computed-Return
- app.config.ts Override-Pfad `op.{component}` dokumentiert und typisiert
- `ui` Prop Pattern auf OpSection und OpSlot
- Dark Mode via Standard-Tailwind `dark:` Variante
- Theme-Registration via `registerTheme()` + Nuxt Module
- SSR-kompatibel (synchrone Resolution)
